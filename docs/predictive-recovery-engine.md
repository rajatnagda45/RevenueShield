# Predictive Recovery Engine & Expected Value Optimization

This document outlines the architecture, feature schema, mathematical formulation, point-in-time anti-leakage invariants, model lifecycle, explainability, and fallback mechanisms for **Step 8 (Predictive Recovery Engine)**.

---

## 1. Objective & Mathematical Formulation

The Predictive Recovery Engine predicts the probability of successful recovery for a revenue-at-risk case conditioned on candidate recovery interventions:

$$P(\text{recovery} \mid \mathbf{x}, a)$$

Where:
- $\mathbf{x}$: Vector of pre-decision features available at the moment of evaluation.
- $a$: Candidate recovery action (e.g. `SEND_PAYMENT_LINK`, `RETRY_PAYMENT`, `SEND_WHATSAPP_REMINDER`, `SEND_EMAIL_NOTIFICATION`, `OFFER_DISCOUNT`).

### Expected Recovered Value Optimization
Rather than optimizing probability in isolation, the system calculates and ranks actions by **Expected Recovered Value** ($E[V]$):

$$E[V(a)] = P(\text{recovery} \mid \mathbf{x}, a) \times \text{Expected Recoverable Amount}$$

#### Example:
For a case with amount at risk = ₹10,000:
- **Action A (`SEND_WHATSAPP_REMINDER`)**: $P = 0.70 \implies E[V] = \text{₹}7,000$
- **Action B (`SEND_PAYMENT_LINK`)**: $P = 0.85 \implies E[V] = \text{₹}8,500$

Action B is ranked higher because it maximizes expected revenue recovery.

## 2. High-Level Architecture & Guardrails

```
[Razorpay Events & Sync]
          │
          ▼
   [Payment Ingestion]
          │
          ▼
    [RecoveryCase]
          │
          ▼
  [Diagnosis Engine] ───► [Customer Intelligence]
                                 │
                                 ▼
                     [PredictionService]
                     ├── Check ModelRegistry (Active Model?)
                     ├── If Active ML: Predict P(rec | x, a) via Pipeline
                     └── If No Model: Predict P(rec | x, a) via HeuristicPredictor
                                 │
                                 ▼
                     [Rank Actions by E[V]]
                                 │
                                 ▼
                         [DecisionEngine]
                                 │
                                 ▼
                          [PolicyEngine]  ◄── (Enforces Quiet Hours & Attempt Caps)
                                 │
                                 ▼
                         [ExecutionEngine]
```

> [!IMPORTANT]
> **Policy Guard**: Machine learning predictions **never** bypass the `PolicyEngine` or `ExecutionGuard`. A high-scoring ML action will still be blocked if regulatory quiet hours, customer promise-to-pay pauses, or retry limits are violated.

## 3. Feature Schema (`feature_schema_v1`)

### Input Features (Available at Decision Time)

| Feature | Type | Description |
| :--- | :--- | :--- |
| `amount_at_risk` | Numerical | Monetary transaction value at risk (in INR). |
| `case_age_at_decision_hours` | Numerical | Hours elapsed between case creation and decision time. |
| `diagnosis_category` | Categorical | Root cause category (`INSUFFICIENT_FUNDS`, `AUTHENTICATION_FAILED`, etc.). |
| `diagnosis_confidence` | Numerical | Confidence of root cause classification ($0.0 \dots 1.0$). |
| `risk_score` | Numerical | Heuristic risk score ($0 \dots 100$). |
| `heuristic_recovery_probability` | Numerical | Baseline heuristic probability prior to ML ($0.0 \dots 1.0$). |
| `customer_success_rate` | Numerical | Customer's historical payment success ratio ($0.0 \dots 1.0$). |
| `customer_success_count` | Numerical | Number of historical successful payments by customer. |
| `customer_failure_count` | Numerical | Number of historical failed payments by customer. |
| `previous_recovery_attempts` | Numerical | Number of prior interventions executed on this case. |
| `payment_method` | Categorical | Gateway payment instrument (`CARD`, `UPI`, `NETBANKING`, `WALLET`). |
| `bank` | Categorical | Issuing bank code (`HDFC`, `ICICI`, `SBIN`, etc.). |
| `error_code` | Categorical | Gateway error code (`BAD_REQUEST_ERROR`, etc.). |
| `error_source` | Categorical | Originator of failure (`ISSUER_BANK`, `CUSTOMER`, `GATEWAY`). |
| `error_step` | Categorical | Transaction lifecycle step (`PAYMENT_AUTHORIZATION`, etc.). |
| `error_reason` | Categorical | Specific decline reason code. |
| `action_type` | Categorical | Evaluated candidate action (`SEND_PAYMENT_LINK`, `RETRY_PAYMENT`, etc.). |
| `decision_score` | Numerical | Candidate score generated by decision engine. |
| `decision_confidence` | Numerical | Confidence score of candidate action. |

### Forbidden Attributes (Anti-Leakage Validation)
To eliminate future information leakage, the validator `validate_point_in_time_features()` strictly rejects snapshots containing:
- `amount_recovered`, `recovered_amount`, `outcome_type`, `payment_captured_at`, `recovery_percentage`, `time_to_recovery`, `final_payment_status`, `attribution_type`, `label`, `is_recovered`.

## 4. Data Sufficiency & Fallback Strategy

Before fitting models on production `REAL` data, `TrainingPipeline.check_sufficiency()` enforces:
1. `total_examples >= 50`
2. `positive_examples >= 10`
3. `negative_examples >= 10`
4. Balanced class ratios.

If thresholds are not met, the system returns `INSUFFICIENT_DATA` and seamlessly operates on the deterministic `HeuristicPredictor` baseline.

---

## 5. Model Registry & Activation

The `model_versions` table maintains model provenance and lifecycle states:
- `TRAINING`: Fitting in progress.
- `VALIDATED`: Training and evaluation completed successfully.
- `ACTIVE`: Champion model actively serving production inferences.
- `RETIRED`: Previous active champion superseded by a newly activated model.
- `DEVELOPMENT_ONLY`: Synthetic demo models trained for verification.
- `INSUFFICIENT_DATA`: Real dataset threshold unfulfilled.

---

## 6. Explainability

Predictions include non-causal associative explainability factors:
- "Associated with `AUTHENTICATION_FAILED` diagnosis pattern (confidence 90%)."
- "Customer historical success rate of 85% (5 captured, 1 failed)."
- "Action `SEND_PAYMENT_LINK` predicted recovery probability 84%."

Associative terminology is intentionally used because predictive association does not imply counterfactual causality.
